Native HomeDash UI Simulator Plan

Goal: make it possible to preview and interact with the real HomeDash LVGL UI on the desktop without flashing the ESP32-S3 device.

Current State

  • The repository already has a sim/ directory with an SDL2-based LVGL simulator.
  • The checked-in sim/homedash_sim binary is not usable on this Windows machine; its header is Mach-O, so it is an old macOS binary.
  • sim/Makefile assumes Unix tools: make, gcc/g++, sdl2-config, find, and grep.
  • Those tools are not currently available in this Windows shell.
  • sim/main_sim.cpp uses old LVGL display/input APIs such as lv_disp_drv_t and lv_disp_draw_buf_t, while the firmware now uses LVGL 9.2.2.
  • The simulator source has a hardcoded Bridge URL and API key. That should be removed before relying on the simulator.
  • After AgentDeck removal, the simulator also needs an additional stub for request_ota_check().

Desired Behavior

  • Run a desktop window sized 1024x600 that renders the same src/ui_dashboard.cpp UI used by firmware.
  • Support mouse/touch-like interaction for tileview swipes, calendar clicks, the Today button, light buttons, and the OTA button stub.
  • Use fixture data by default so the simulator works offline and never requires real secrets.
  • Optionally load Bridge data from environment variables for realistic manual checks.
  • Provide a single documented command for this Windows machine.
  • Keep simulator changes isolated from firmware behavior and OTA release flow.

Recommended Approach

Use a native desktop SDL2 simulator, but modernize it for LVGL 9 and make it Windows-friendly. The simulator should continue to compile the real UI source instead of building an HTML imitation, because the goal is to catch layout, font, tileview, and calendar behavior before flashing.

Prefer a small simulator-specific build setup over changing firmware build settings. If a bundled or already-installed compiler/SDL2 is available, use it. If not, document the missing prerequisite clearly before installing anything.

Likely File Changes

  • sim/main_sim.cpp: port display/input glue from LVGL 8-style APIs to LVGL 9 APIs.
  • sim/stubs.cpp: update or remove stale module stubs; add request_ota_check(); ensure Bridge accessors match current firmware headers.
  • sim/Makefile or new simulator build file: make the build reproducible from Windows.
  • sim/fixtures/ or similar: add sample dashboard/calendar payloads for offline UI preview.
  • README.md and/or AGENTS.md: document simulator build/run commands and limitations.
  • .gitignore: keep simulator build outputs ignored, not source fixtures or build scripts.

Implementation Steps

  1. Audit available local toolchains: Node/Python bundles, PlatformIO packages, CMake, MSVC, MinGW, SDL2 availability.
  2. Choose the least invasive desktop build path that works on this machine.
  3. Port the LVGL simulator glue to LVGL 9:
    • create display with lv_display_create(1024, 600);
    • set draw buffers with lv_display_set_buffers;
    • register flush callback with LVGL 9 signature;
    • create pointer input with lv_indev_create().
  4. Replace hardcoded Bridge credentials with fixtures by default and optional environment variables such as HOMEDASH_SIM_BRIDGE_URL and HOMEDASH_SIM_BRIDGE_KEY.
  5. Populate realistic fixture data for weather, calendar, transport, health, tasks, news, lights, and sensors.
  6. Build the simulator locally.
  7. Run it and visually verify all 3 pages, calendar click behavior, Today button, tile navigation, and Page 3 button stubs.
  8. Update docs and AGENTS.md with the final command.

Test Plan

  • Simulator build command passes from a clean shell.
  • Firmware build still passes with C:\Users\me\.platformio\penv\Scripts\pio.exe run.
  • Simulator opens a 1024x600 window and renders nonblank UI.
  • Page indicator dots update while swiping/click-dragging between pages.
  • Calendar date click changes the schedule title and invokes simulator calendar data flow.
  • Today button returns the schedule to the current date.
  • Page 3 OTA button prints a simulator log instead of attempting firmware update.
  • No real secrets are present in source code or committed fixtures.

Risks

  • SDL2 may not be installed locally. If so, we need either a lightweight install step or a different build path.
  • LVGL 9 desktop APIs may need small config changes, and those changes must not bloat firmware builds.
  • Simulator rendering is useful for layout and interactions, but it cannot validate ESP32-specific LCD tearing, PSRAM, DMA, WiFi, OTA, or touch-controller behavior.
  • Real Bridge live data may expose secrets if handled casually; fixture-first mode avoids that.

Rollback Plan

  • Simulator work is isolated under sim/ plus documentation. If it fails, revert those files without touching firmware source.
  • If a shared config change is required and later proves risky, restore the previous firmware lv_conf.h behavior and keep simulator-only config separate.
  • Do not tag or release firmware as part of this simulator task.

Open Questions

  • Should live Bridge data be supported in the first pass, or should the first pass be fixture-only?
  • Is installing a missing Windows build prerequisite acceptable, or should the solution only use tools already installed on this machine?
  • Should screenshots from the simulator be part of the workflow for UI review?

Approval Gate

No simulator implementation or build-tool changes should happen until this plan is approved. After approval, implementation should stop before any firmware flash. This task does not require flashing the ESP32-S3.

Actual Changes

  • Replaced the stale SDL2 simulator entrypoint with a Windows Win32/LVGL 9 simulator in sim/main_sim.cpp.
  • Added sim/build_windows.ps1, which uses the installed Visual Studio C++ tools and builds sim/build/windows/homedash_sim.exe.
  • Reworked sim/stubs.cpp to use fixture data and removed the hardcoded live Bridge URL/API key.
  • Added simulator-only compatibility for Windows localtime_r and ESP heap stubs under sim/esp_stubs/.
  • Documented the simulator command in README.md and AGENTS.md.
  • Added .superpowers/ to .gitignore for brainstorming companion output.

Checks Run

  • powershell -ExecutionPolicy Bypass -File sim\build_windows.ps1 passed and produced sim/build/windows/homedash_sim.exe.
  • The simulator was launched as a GUI app and rendered the HomeDash first page with fixture data in a 1024x600 LVGL window.
  • The user confirmed the simulator works locally.
  • C:\Users\me\.platformio\penv\Scripts\pio.exe run passed after simulator changes.
  • A simulator rebuild while the window was still open failed because Windows locked homedash_sim.exe; after closing the simulator process, the rebuild passed.

Known Limitations After Implementation

  • The simulator is fixture-only for now; it does not fetch live Bridge data.
  • It validates desktop LVGL layout and mouse interaction, not ESP32 hardware display timing, PSRAM/DMA, WiFi, OTA, or the GT911 touch controller.
  • It currently depends on Visual Studio C++ tools being installed at one of the scripted paths.
